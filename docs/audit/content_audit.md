# So'z Jangi — Word-Content Subsystem Audit

**Scope:** read-only audit of the word-content subsystem after the Supabase
integration and the introduction of `tool/corpus/output/words_import.sql`.
**Date:** 2026-07-15 · **Mode:** audit only — no code, data, or schema changed.

---

## SECTION 1 — CURRENT WIRING (facts)

There are **two parallel content paths** in the running app. Practice/Bonus read
bundled assets; Daily is fully server-authoritative on Supabase.

### (a) Valid-guess validation words
- **Practice / Bonus:** bundled gzip asset `assets/dictionary/valid_guesses.txt.gz`,
  loaded into `_validKeys` by `SupabaseAssetDictionary._loadValidGuesses`
  ([lib/data/dictionary_datasource.dart:176](../../lib/data/dictionary_datasource.dart#L176)).
- **Daily:** two-stage. Local pre-check `_dictionary.contains(word)` against the
  same bundled set ([daily_cubit.dart:267](../../lib/features/daily/presentation/daily_cubit.dart#L267)),
  then the **authoritative** check is server-side inside the `evaluate-guess`
  Edge Function, which returns `error: 'not_a_word'`
  ([supabase_daily_puzzle_repository.dart:78](../../lib/features/daily/data/supabase_daily_puzzle_repository.dart#L78)).

### (b) Answer words
- **Practice / Bonus:** bundled `assets/dictionary/answers_tiered.tsv.gz` →
  `_answerPool` / `_answersByTier` (`_loadAnswers`,
  [dictionary_datasource.dart:184](../../lib/data/dictionary_datasource.dart#L184)).
- **Daily:** the answer is **never on the client**. Guesses are scored by the
  `evaluate-guess` Edge Function, which alone holds the answer; the plaintext is
  returned only on win/final-reveal
  ([supabase_daily_puzzle_repository.dart:47](../../lib/features/daily/data/supabase_daily_puzzle_repository.dart#L47)).

### (c) Daily schedule / metadata
- **Live path:** `SupabaseDailyPuzzleRepository.fetchMeta` selects from the
  **`daily_puzzle_public` view** (columns `puzzle_number, puzzle_date,
  word_length, theme, locked_prefix_raw` — no answer)
  ([supabase_daily_puzzle_repository.dart:30](../../lib/features/daily/data/supabase_daily_puzzle_repository.dart#L30)).
- **Dead path:** `SupabaseAssetDictionary.answerForDate` /
  `puzzleNumberForDate` (bundled `schedule.json.gz` + REST poll of the
  `daily_puzzles` table) **has no remaining caller in `lib/`** (verified by
  grep). The whole Supabase-schedule-refresh + bundled-schedule answer machinery
  in the datasource is now **orphaned code** relative to Daily.

### (d) Definitions
- **Practice / Bonus:** `_dictionary.definitionFor(answer)`
  ([practice_cubit.dart:113](../../lib/features/practice/presentation/practice_cubit.dart#L113),
  [bonus_cubit.dart:102](../../lib/features/bonus/presentation/bonus_cubit.dart#L102)).
  Note: `_definitionByKey` is only populated by `_ingest` (Supabase rows +
  bundled schedule), **not** from `answers_tiered.tsv.gz` — so Practice/Bonus
  definitions exist only for words that also appear in the 90-day schedule; every
  other answer returns `null`. (Pre-existing behaviour, not caused by this change.)
- **Daily:** definition is not surfaced through the new view path (`fetchMeta`
  does not select it); `daily_puzzles.definition_uz` feeds only the legacy path.

### Was the datasource rewired away from bundled-assets + Supabase-schedule?
**Yes, for Daily.** DI still registers `SupabaseAssetDictionary` as the
`Dictionary` ([service_locator.dart:62](../../lib/core/di/service_locator.dart#L62)),
but `DailyCubit` now takes a separate `DailyPuzzleRepository`
(`SupabaseDailyPuzzleRepository`) and uses it for **all** answer/metadata/scoring
([service_locator.dart:130](../../lib/core/di/service_locator.dart#L130),
[daily_cubit.dart:128/232/278](../../lib/features/daily/presentation/daily_cubit.dart#L128)).
The Dictionary is reduced, for Daily, to a local `contains()` guard. Practice and
Bonus are unchanged (still 100% bundled assets).

### Is `words_import.sql` referenced anywhere?
**No.** Zero references in `lib/`, migrations, seeds, or build scripts. It is an
**orphan artifact** relative to the repo: it targets a `public.words` table for
which **no migration exists in the repo**. It is generated by (also untracked)
`tool/corpus/export_supabase.py`. Its likely real consumer is the server-side
`evaluate-guess` Edge Function's dictionary check — but neither that function nor
the `words` table DDL is in the repository, so this cannot be confirmed here.

### Supabase migrations / tables present in the repo
| Object | Where | Purpose |
|---|---|---|
| `daily_puzzles` (table) | `supabase/migrations/20260710000001_daily_puzzles.sql` | Legacy daily distribution: `date, word, definition_uz, difficulty`. RLS: SELECT-only, released dates ≤ tomorrow (Asia/Tashkent). |
| `daily_puzzles` seed | `supabase/seed/seed_daily_puzzles.sql` | 90-day upsert, 2026-07-10 … 2026-10-07. |
| **`daily_puzzle_public` (view)** | **not in repo** | Read by the live app (`fetchMeta`). DDL absent. |
| **`evaluate-guess` (edge fn)** | **not in repo** (`supabase/functions/` does not exist) | Authoritative scoring + word validation. |
| **`public.words` (table)** | **not in repo** | Target of `words_import.sql`. DDL absent. |

**Gap:** the three objects the live app actually depends on (`daily_puzzle_public`,
`evaluate-guess`, and the `words` table the import feeds) exist only in the remote
project, not as tracked migrations. This is a reproducibility / provenance gap.

## SECTION 2 — PROVENANCE OF `words_import.sql`

`words_import.sql` is **not hand-authored and not LLM-generated.** It is a
mechanical 1:1 export of the curated corpus (`export_supabase.py` reads
`out/valid_guesses.txt` + `out/answers_tiered.tsv`). Verified:

- **6766** word rows (14 batched `INSERT`s), `ON CONFLICT (word) DO NOTHING`.
- Row set **== `upper(valid_guesses.txt)` exactly** (0 added, 0 dropped).
- **1816** rows flagged `is_answer_candidate = true` == `upper(answers)` exactly.
- 4950 guess-only rows (`is_answer_candidate = false`, tier `standart`).

### Cross-check against the MUNIS hunspell stem list (`uz_Latn_UZ.dic`)
Independently reproduced from `tool/corpus/data/raw/uz_Latn_UZ.dic`
(75 537 entries; 69 446 well-formed lowercase stems; 5143 that are 5 logical
letters) using the project's own tokenizer and inflection validator:

| Bucket | Count | % |
|---|---:|---:|
| (a) exact MUNIS 5-letter stems | **5140** | 76.0% |
| (b) MUNIS-derivable inflected forms | **1626** | 24.0% |
| (c) NEITHER — no dictionary provenance (LLM-shaped) | **0** | 0.0% |

- (a) is 5143 minus the 3 offensive stems dropped from the guess list.
- (a)+(b) = 6766 = every word. **Bucket (c) is empty**, so there are **no
  40 samples to output** — every word in `words_import.sql` roots to a real
  MUNIS lemma. This matches the build's own provenance
  (`build_stats.json → vg_sources`: answer 2839, hunspell_stem 2301,
  generated_inflection 1124, wiki_inflection 502).

**Conclusion:** the earlier concern that `words_import.sql` might be LLM-generated
content is **not supported**. It carries full MUNIS + Wikipedia-frequency
provenance and is safe on that axis.

## SECTION 3 — QUALITY SCAN of `words_import.sql`

Automated heuristics over the 6766 words:

**(a) Suffixed / inflected forms where the stripped stem is itself a MUNIS word — 772.**
This is expected and legitimate (they are the accepted-guess inflections, not
answers). Samples: `asrga, aybni, bahsi, chelni, choʻlni, dilda, eriga, ishida,
ishqni, jizni, kodni, oʻtlar, shonda, suvda, tupda, uyiga, yoʻlim, yuzda, yuzga,
eskicha`. None are answer candidates by construction (answers are noun lemmas).

**(b) Russian/European borrowing-shaped — 124** (initial clusters
vz/st/sk/shk/sht/br/gr/kr/pr/tr/pl/kl/fl/vr/sp/… + `-tsiya/-siya/-izm`). These are
**loanwords already present in the MUNIS lexicon** and standard in written Uzbek;
they are valid guesses, and (being non-nouns/technical) largely not answers.
Samples: `blank, bluza, flyus, grant, grunt, klubi, plata, plyaj, shkafi,
shtanga, shturm, skuns, splin, sport, stela, stoli, trend, shtrek, shteyn,
klani`. **Not defects** — flagged for awareness only.

**(c) Interjections / onomatopoeia.** No reliable automated signal; MUNIS `po:`
tags do not mark interjections and reduplication heuristics over-match. Not
quantified. Given every word is MUNIS-rooted and answers are noun-only, the risk
of an interjection *answer* is low; a manual spot-review of the guess list is the
only way to be certain.

**(d) Entries not exactly 5 logical letters — 0.** Every word tokenizes to
exactly 5 logical letters under the 29-letter alphabet; the `length` column is 5
on every row. Clean.

**(e) Duplicates / case inconsistencies — 0.** No duplicate rows, no
case-fold collisions. `ON CONFLICT (word) DO NOTHING` additionally guards the DB.

**(f) Offensive exclusion list — 0.** No word in `words_import.sql` (nor in the
answer pool) matches `exclusions/offensive_uz.txt` (57 terms, substring match for
≥4-char roots). The build removed 3 offensive stems upstream.

## SECTION 4 — COLLATERAL STATE

**90-day schedule** — `tool/generator/out/schedule.json` → bundled
`assets/dictionary/schedule.json.gz` → `supabase/seed/seed_daily_puzzles.sql`,
all three consistent (identical 90 words, 2026-07-10 … 2026-10-07, each with a
definition). Generated by `generate_schedule.py` from `answers_tiered.tsv`.
**Staleness finding:** all 90 words are valid guesses, but **18 of 90 are no
longer in the current answer pool** (`answers_tiered.tsv`). They are non-nouns
that the recuration's noun-only answer restriction excludes:
`toʻlin, hamma, lirik, nodon, ruhli, sochli, taxir, lokli, tipik, ensiz, batang,
zarur, ziyod, moviy, chunki, rangin, tanli, arzon`. The schedule was generated
against an **older, broader answer pool** and was not regenerated after
recuration (`build_stats.recurated = true`, 1023 rare-tail answers dropped). The
game still functions (server validates guesses; these are all valid words), but
words like `chunki` ("because", a conjunction) and `hamma` (pronoun) as daily
answers reflect the pre-recuration pool.

**WS1 definitions** — `tool/generator/definitions_uz.json` (90 entries) attach
**only to the 90 scheduled daily words**, keyed by word so they survive a
re-cut. They are carried in `schedule.json.gz` and `seed_daily_puzzles.sql`. They
do **not** cover the broader corpus, and `words_import.sql` writes `theme`/
definition as NULL for all rows (definitions are not exported to `words`).

**Tier structure** — balanced: answers 605 easy / 605 mid / 606 hard
(`oson`/`oʻrta`/`qiyin`). In `words_import.sql`: 1816 tiered answer candidates +
4950 `standart` guess-only. Consistent with `build_stats.json`.

**answers ⊆ valid_guesses invariant** — **holds** (1816 ⊆ 6766, 0 missing).
Enforced twice: `build_corpus.py` assertion and `export_supabase.py` assertion.

**Previous curated pipeline outputs** — **intact.**
`tool/corpus/out/{answers.txt (1816), answers_tiered.tsv (1816),
valid_guesses.txt (6766), build_stats.json, validation_report.md}` all present
and mutually consistent; the bundled gzips derive from them. The MUNIS +
Wikipedia sources (`data/raw/uz_Latn_UZ.dic`, `wiki_freq.tsv`) are present. The
git diff shows these were regenerated (recurated), not deleted or replaced.

## SECTION 5 — VERDICT TABLE

- **Dictionary source of truth (Practice/Bonus = bundled MUNIS corpus)** —
  **KEEP.** Fully provenanced, invariants hold, 0 quality defects.
- **Daily answer/validation source (Supabase `daily_puzzle_public` view +
  `evaluate-guess` edge fn)** — **KEEP (design)** but **FIX (repo hygiene):** the
  view, edge function, and `words` table DDL are not tracked as migrations —
  add them so the backend is reproducible from the repo.
- **`words_import.sql`** — **KEEP.** Legitimate mechanical export of the curated
  corpus, 0 orphan/LLM content. Caveat: it targets a `words` table whose
  migration is missing — track that migration alongside it.
- **`export_supabase.py`** — **KEEP** (currently untracked/new): it is the single
  bridge preventing Practice's local dict and Daily's `words` table from
  diverging. Commit it.
- **90-day schedule + `seed_daily_puzzles.sql`** — **FIX.** Regenerate from the
  current recurated `answers_tiered.tsv` so the 18 out-of-pool (non-noun) daily
  answers are replaced; three copies (generator/asset/seed) stay in sync.
- **WS1 definitions (`definitions_uz.json`)** — **KEEP**, re-attach on schedule
  regeneration (keyed by word, so they survive). Optionally extend coverage
  beyond the 90 scheduled words for Practice/Bonus, which today get `null` for
  any non-scheduled answer.
- **Legacy `daily_puzzles` table + `SupabaseAssetDictionary.answerForDate`/
  schedule-refresh path** — **DELETE / decommission (deferred):** dead code with
  no caller now that Daily uses the view + edge function. Removing it also
  resolves the `dart:io` web-build blocker noted for this datasource. Confirm the
  `daily_puzzle_public` view does not read `daily_puzzles` before dropping the
  table.
